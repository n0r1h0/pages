START — Mental Model

最初に掴む、一本のメッセージ

LLMは「思考と言語のエンジン」です。AIサービスは、そのエンジンへ必要な情報を渡し、現実の道具を使わせ、結果を検証するシステムです。

この文書の主張：「特化AI」の価値の多くは、独自モデルそのものではなく、汎用モデルを特定業務で迷わせず、失敗を検出できる設計にあります。
① Model / 重み
言語、一般知識、推論、指示追従などの基礎能力。学習済みの数値パラメータ。
② Context / 文脈
今回の依頼、会話履歴、資料、システム指示、ツール定義など、その呼び出しで読ませる情報。
③ Skill / 手順
何を優先し、どの順で進め、何を完成とみなすかを定義する再利用可能な業務手順。
④ RAG & Tools
外部の最新・固有情報を取得し、検索、計算、コード実行、業務操作などを行う能力。
⑤ Loop / Harness
モデルを呼ぶ、ツールを実行する、結果を戻す、検証し再試行する外側の制御プログラム。
⑥ Evals / 品質管理
正解率、引用、形式、失敗率、コスト、速度を測り、改善を続ける仕組み。
1

Skillは注意の設計

知識を大量に足すより、AIが迷う箇所を、判断基準・工程・検査へ変換します。

2

Loopは外側のコード

プロンプトは判断方針。再呼び出し、ツール実行、停止、承認は通常プログラムが担います。

3

コンテキストは有限資源

SkillやRAGは入力を消費します。量だけでなく、重要情報の密度と配置が性能を左右します。

1. 区別するモデルとサービス
2. 方向づけるSkillと文脈
3. 動かすツールとループ
4. 具体化するChatGPTの一例

実用上の品質 ≈ 基盤モデル × 文脈設計 × 実行制御 × 外部能力 × 評価改善
※数学的な式ではなく、どれか一層が弱いと全体品質が下がる、という設計上の比喩です。
この章の結論モデルの能力と、サービスの制御・情報・道具・評価を分けて考えると、以降の概念がすべて整理できます。

01 — Model vs Service

まず区別する：モデルとAIサービス

「何かに特化したAI」という表現は、モデルの重みが特化している場合と、汎用モデルの周辺システムが特化している場合を混ぜています。

同じGPTやClaudeを使っていても差が出るのは、何を読ませ、何をさせ、どの順で進め、どう失敗を検出するかが異なるからです。
呼ばれ方実態モデルの重み
真の特化モデル追加事前学習、SFT、DPO、RFT、LoRAなどで振る舞いを変更変わる
特化AIシステム汎用LLM＋RAG＋Skill＋ツール＋ループ＋検査変わらないことが多い
モデルルーター型分類、検索、推論、画像、安全判定を複数モデルへ分業各モデルは既製でもよい
プロンプトラッパー長い指示と専用UIを加えた比較的薄い実装変わらない

「GPT x.xを使っています」は何を意味するか

サービスが公開APIの特定モデルIDをそのまま呼び出しているなら、通常、そのサービス提供者が重みを変更しているわけではありません。重みを追加学習した派生は、技術的には別のモデル／デプロイメントとして扱われます。

ただし、宣伝上の「GPT x.x搭載」「powered by〜」だけでは、完全に素のモデルか、ルーティング、蒸留、独自派生、複数モデル併用を含むかは判定できません。名称よりも、どの層を独自実装しているかを確認する必要があります。

サービス提供者が実際に作るもの

知識基盤

文書取り込み、分割、検索、メタデータ、権限、更新管理、再順位付け。

業務制御

意図分類、工程分岐、状態保存、ツール連携、承認、例外処理。

品質基盤

評価データ、形式検証、引用検査、失敗ログ、A/Bテスト、監査。

RAGは「検索を1回するだけ」ではない

実用的なRAGは、質問の分類、検索語の書き換え、キーワード＋意味検索、権限フィルタ、鮮度判定、再順位付け、重複排除、必要箇所抽出、引用整合性確認まで含みます。RAGはモデルの重みを変えず、実行時に参照資料を選ぶ仕組みです。

この章の結論モデル名が同じでも、文脈・検索・ツール・ワークフロー・評価が違えば、サービス品質は大きく変わります。

02 — Skill

Skillの核心は「仕事の進め方」の外部化

Skillは「専門家として振る舞え」という役割設定ではありません。曖昧な仕事を、安定して実行できるワークフローへ変換するものです。

Skillとは、目的・発動条件・手順・判断基準・使う道具・完成条件・失敗時の処理をまとめた、再利用可能な作業モジュールです。

OpenAIの現行APIドキュメントでも、Skillはファイル群と SKILL.md からなるバージョン管理可能な束であり、会社のスタイルガイドから複数段階のワークフローまで、プロセスや慣行をコード化するものと説明されています。[1]

悪い指示

「良いレポートを作って」「専門家として完璧に」「必要なら検証して」

自由度が高く、終了条件も曖昧。モデルは“もっともらしい完成”を選びやすい。

良いSkill

対象を分類 → 根拠を取得 → 判断 → 出力スキーマへ整形 → 機械検査 → 不合格なら修正。

迷いが生じる場所にだけ、具体的な制約と判断軸を置く。

良いSkillの7要素

要素役割例
発動条件いつ使うかPDF作成、契約レビュー、障害調査など
目的何を最適化するか正確性、短さ、引用、可読性、再現性
工程作業の順番入力確認 → 設計 → 作成 → 検査 → 修正
判断基準分岐のルール情報不足なら検索、数値がなければ推測しない
ツール選択実際の能力へ接続検索、コード、DB、ブラウザ、ファイル操作
完成条件終わりを定義形式エラーなし、根拠あり、指定項目を網羅
例外処理失敗時の行動再検索、縮退動作、人間へエスカレーション
設計のコツすべてを縛るのではなく、AIが誤った選択をしやすい地点だけを拘束します。Skillは「自由を消すもの」ではなく、「重要な判断に確率を集中させるもの」です。
なぜ人間はSkillなしで動けるように見えるのか

人間にもSkillはあります。ただし、反復経験によって目的保持・注意・習慣・身体的な試行へ内在化されているため、毎回マニュアルを意識していないだけです。

人間

目的を保持する注意、習慣・手続き記憶、身体による試行、環境からの即時フィードバックを持つ。

素のLLM

大量のパターン知識は持つが、現在の目的、現実世界の状態、結果の成否が自動では結びつかない。

人間の情報選択を支えるもの

現在の目標何をしようとしているか
→
選択的注意関連情報を優先
→
学習済みの塊手順をチャンク化
→
行動小さく試す
→
環境の反応誤差を修正

認知研究では、ワーキングメモリが現在のタスクセットを保持し、目標に沿って知覚的注意を制御するという整理があります。[9] また、反復された行動は習慣化し、意識的な逐次判断を減らす効率的な既定反応になります。[10]

「attention」という名前に注意

Transformerのattentionは、入力中のトークン同士の関係を計算して情報を混合する機構です。人間のように、身体、長期目標、価値判断を統合して「これは今の仕事に重要だ」と自覚的に選ぶ注意機構と同一ではありません。Transformerの基礎構造は、attention機構を中心に設計されています。[12]

LLMが苦手になりやすい理由

学習目標と業務成功が同一ではない

典型的な基礎学習は、文脈から次のトークンを高精度に予測する方向で能力を形成します。指示学習や推論学習で改善されても、今回の業務が現実に完了したかは外部検証が必要です。

目的が入力の一部にすぎない

ユーザーの目的、補足、例、雑談、制約が同じトークン列に並びます。何が最重要かは推定が必要です。

推論中に重みは通常更新されない

会話内で一時適応はできますが、毎回の経験が恒久的な技能へ自動変換されるわけではありません。

身体と現実の連続状態がない

ツールや状態管理がなければ、実際に作業が成功したかを直接観測できません。

文章の一貫性と正しさが分離する

最初の解釈を誤ると、その誤った前提に一貫した文章を生成できます。

人間も万能ではない初めての仕事、高リスク作業、注意が散りやすい状況では、人間もマニュアル、チェックリスト、テンプレートを必要とします。違いは「Skillの有無」ではなく、どれだけ内在化されているかです。
この章の結論Skillは知識集ではなく、モデルが誤りやすい選択点を、手順・判断基準・検査へ変えるものです。

03 — Weights, Context & RAG

重み・コンテキスト・RAGを混同しない

モデルを変える方法と、その場で材料を渡す方法は別です。この区別が、fine-tuningとコンテキスト消費の議論を整理します。

方法どこを変えるか実行時コンテキスト主用途
Fine-tuningモデルの重み学習例そのものは毎回入れない安定した形式・分類・行動傾向
System prompt今回の入力消費する役割、優先順位、制約
Few-shot今回の入力消費する例から形式・判断を誘導
Skill今回の入力＋ファイル／コード読んだ部分は消費する工程、判断基準、検査
RAG今回の入力取得文書が消費する最新・社内・案件固有情報
Tool definition今回の入力消費する利用可能な行動をモデルへ説明

OpenAIのモデル最適化ガイドでは、プロンプトは文脈・指示・目標を与え、fine-tuningはモデルを特定タスクで優れたものにする別手段として整理されています。fine-tuningは、単一リクエストのコンテキストに収まらない多数の例を学習でき、実行時のプロンプトを短くできる利点があります。[5]

コンテキスト上限 ≈ 入力トークン + 推論トークン + 可視出力トークン
モデル・APIにより厳密な会計方法や、過去ターンの推論情報の保持方法は異なります。

「Skillを増やすほどthinkが減る」はどこまで正しいか

物理的な最大余白については正しいです。OpenAIの推論モデルでは、内部推論トークンもコンテキストウィンドウを占有し、複雑な問題では数百から数万トークンになり得るため、推論・出力用の余白を確保する必要があります。[4]

ただし、上限まで大きな余裕があり、実際のタスクが短い推論しか必要としないなら、Skillが数千トークン増えても品質が比例して落ちるとは限りません。

容量の問題

固定指示、会話履歴、RAG、ツール結果が増えるほど、推論と出力に使える最大領域が減ります。

信号密度の問題

上限内でも、無関係な情報が増えると重要情報の選択が難しくなります。長いほど必ず良いわけではありません。

長いコンテキストを受け取れることと、その全域を頑健に利用できることは別です。「Lost in the Middle」研究では、関連情報の位置が中央になるだけで性能が下がるモデルが確認されました。[11]

圧縮・キャッシュ・外部状態は別物

仕組み減らすもの減らさないもの
Prompt cache再計算、レイテンシ、料金の一部コンテキスト占有量
Compaction履歴のトークン量情報損失のリスク
RAG再取得常時保持する文書量検索ミスのリスク
構造化状態長い会話履歴への依存設計・保守コスト

Anthropicの公式ドキュメントも、システムプロンプト、メッセージ、ツール結果、画像、文書、ツール定義、生成出力とthinkingがコンテキストに数えられ、キャッシュされた入力もウィンドウを占めると説明しています。[7]

良い設計全Skill・全資料・全ツールを毎回渡さず、短いメタデータから必要なものだけ選び、必要な部分だけ読み、作業済みの巨大な結果は構造化して外へ保存します。
コンテキストが大きいなら、全部入れてもよい？

いいえ。上限内でも、無関係な情報が増えるほど信号密度が下がります。全Skill・全ツール・全資料を常時投入せず、必要なものを遅延読み込みする設計が有効です。

また、プロンプトキャッシュは再計算や料金を減らしても、通常はコンテキスト占有そのものを減らしません。

この章の結論Fine-tuningは重みに寄せる手段。Skill・RAG・プロンプトは、その呼び出しで読む材料です。後者は有限なので、選択と編集が必要です。
仕組み・実装
04 — Execution Loop

実行ループはプロンプトではなく、外側のプログラム

プロンプトは「どう判断するか」。ループは「モデルを再び呼ぶ」「ツールを本当に実行する」「止める」を担当します。

1. モデルを呼ぶ依頼＋指示＋ツール定義
→
2. 行動を選ぶ回答またはツール要求
→
3. 外部実行検索・計算・API・ファイル
→
4. 結果を戻す新しい文脈へ追加
↺
5. 終了完成条件を満たす

OpenAIのFunction Callingでは、モデルがツール呼び出しを返し、アプリケーション側がコードを実行し、結果をモデルへ戻し、最終回答または追加ツール呼び出しを受け取る5段階の流れが明示されています。[2]

messages = [system_instructions, user_request]

for step in range(MAX_STEPS):
    output = call_model(messages, tools)

    if output.is_final:
        return validate_and_return(output)

    if output.is_tool_call:
        assert permission_allows(output.tool)
        result = execute_tool(output.tool, output.arguments)
        messages += [output.tool_call, summarize_if_large(result)]

raise MaxStepsExceeded()

固定ワークフローとエージェント

固定ワークフロー

工程と分岐をコードが決め、各工程でLLMを使います。

安定性、監査、予測可能性が高い。業務処理に向く。

エージェントループ

次に使うツールや調査経路をLLMが動的に選びます。

未知の経路に柔軟。コスト・停止・再現性の管理が必要。

OpenAI Agents SDKのRunnerは、最終出力が出るまで、ハンドオフやツール実行を含むループを管理します。[3] Anthropicも、クライアントツールではClaudeが構造化された呼び出しを返し、アプリケーションが実行する構造を説明しています。[8]

Skill／プロンプトとコードの境界

制御内容置く場所理由
何が不足しているかSkill / Prompt意味的判断が必要
どの情報源を優先するかSkill / Prompt状況に応じた選択
最大試行回数Code確実に守る必要
タイムアウト・予算Code物理的な制限
JSONスキーマCode＋Prompt生成を誘導し、機械検証する
送信・購入・削除の承認Code / Workflow取り消せない操作をモデル判断だけにしない
回答の意味的十分性LLM評価＋可能な確定検査完全な機械判定が難しい
原則：曖昧な意味判断はLLMへ。確実に守らせたい制御はプログラムへ。
「必要なら何度も検索して」と書くだけでループになる？

なりません。プロンプトは検索を選ぶ方針を与えられますが、モデルを再呼び出しし、検索を実行し、結果を戻すのは外側のハーネスです。文章だけのプロンプトは、現実の反復処理を保証できません。

この章の結論モデルは「次に何をするか」を柔軟に選び、プログラムは「実際に行う・制限する・止める」を確実に管理します。

05 — Layered Loops

提供側のループの上に、さらにループを作る意味

有効です。ただし、同じ目的の自己批評を二重化するのではなく、異なる粒度と責任を持つループを重ねる場合に限ります。

内側のループ

一つの調査や生成を完了するため、検索、ツール利用、再検討を行う。

モデル提供者やAgent SDKが管理することもある。

外側のループ

業務全体の工程、検証、承認、再試行、保存、エスカレーションを管理する。

アプリケーション提供者の責任領域。

外側：案件受付形式・権限確認
→
内側：調査検索→読解→追加検索
→
外側：検証スキーマ・根拠・テスト
→
人間承認高リスク操作
→
外側：確定保存・送信・監査

外側ループが特に有効な場面

機械的な検証がある

コード生成→テスト→エラーを渡して修正。

工程が独立している

調査→執筆→引用検証を別コンテキストに分ける。

外部への影響がある

メール送信、購入、DB更新前に承認ゲートを置く。

無駄になりやすい二重ループ

「完璧になるまで自己批評して書き直す」内側と外側が同じ曖昧な基準で批評を続けると、言い換えの反復、過剰な無難化、コスト増、終了不能、コンテキスト肥大化が起きます。

外側の再試行を行うなら、同じ入力で祈るのではなく、明確な不合格理由、追加情報、テスト結果、変更された制約を次の試行へ渡す必要があります。

この章の結論ループを重ねる価値は、反省回数を増やすことではなく、タスク内の探索と業務全体の保証を別責任に分けることにあります。
具体例
06 — ChatGPT as a System

ChatGPTはモデル単体ではなく、実行基盤を含むサービス

このセッションではシステム情報上、私はGPT-5.6 Thinkingとして応答しています。ただし、ChatGPT内部のソースコード、正確なルーティング、非公開のモデル構成を私は観測できません。

ChatGPT Service
会話、ユーザー設定、メモリ候補、指示、ツール、実行ループ、表示、安全制御を管理。
Harness / Runner
入力を組み立て、モデルを呼び、ツール要求を実行し、結果を戻し、必要なら反復。
GPT-5.6 Thinking
与えられたコンテキストから、内部推論、次の行動、ツール要求、回答トークンを生成。
External Tools
Web、計算、コード、ファイル、カレンダー、メールなど、モデル外の現実的な処理。

1ターンの高レベルフロー

入力受付ユーザーの今回の依頼

この章の結論ChatGPTは、モデルに加えて、文脈構築・ツール・実行ループ・状態・安全制御を持つサービスとして理解するのが適切です。

07 — Prepared vs Generated

どこが用意済みで、どこがその場で生成されるのか

回答は「保存済み文章の検索」ではありません。事前学習済みの重みと、今回渡された情報を使い、その場でトークンを生成します。

区分具体例性質
モデルに事前学習済み構造、語彙、重み、言語能力、一般知識傾向、推論・指示追従の能力推論開始前から固定
サービス側に用意済み基本指示、ツール実装、Skillファイル、ループコード、安全・権限機構モデルの外に存在
各ターンで組み立て会話履歴、ユーザー入力、関連メモリ、適用Skill、ツール定義今回の入力コンテキスト
その場で取得Web検索結果、RAG文書、DB結果、計算結果、ファイル内容外部ツールが生成・取得
その場でモデル生成内部推論、ツール呼び出し、回答の構成と文章入力に条件づけられた動的出力

重みの中にあるのは「文書」ではなく、振る舞い

モデルの重みは、個別の記事をファイルとして保持するデータベースではありません。言語パターン、概念間の関係、問題解決の傾向が巨大な数値ネットワークへ分散して符号化されています。

学習済みの重み + 今回のコンテキスト + 動的推論 → 次のトークン → 次のトークン → … → 回答

08 — Design Principles

実装判断を迷わないための原則

A

意味はモデル

曖昧な分類、優先順位、不足情報、自然言語の評価はLLMが得意。

B

保証はコード

回数、権限、予算、形式、トランザクション、承認は決定的コードへ。

C

知識は外部化

更新される事実・社内情報・案件データはRAGやDBへ。

D

反復は証拠付き

再試行にはエラー、テスト、不足項目など具体的フィードバックを渡す。

E

文脈は編集する

全部を残さず、高信号の状態だけを次の呼び出しへ持ち越す。

F

評価から始める

「良い回答」の基準をデータセットと指標にし、モデル変更時も測定する。

タスク別の推奨構成

タスク最小構成必要なら追加
短い翻訳・要約モデル＋短いプロンプト形式検査
社内Q&Aモデル＋RAG＋引用権限、鮮度、再順位付け
契約レビュー固定ワークフロー＋RAG＋Skill条項別エージェント、専門家承認
コード修正モデル＋ファイル／実行ツールテストループ、差分検査
メール送信・購入生成＋明示承認権限、監査、冪等性
探索的リサーチエージェントループ＋検索出典検証、停止条件、コスト上限

典型的なアンチパターン

全Skillを常時投入大量RAGを無選別投入「完璧まで繰り返す」LLMだけで回数制限引用の存在を検査しないテストなし自己批評全履歴を永久保持モデル名だけで品質判断
この章の結論最小構成から始め、失敗の種類が観測できたときだけ、RAG・Skill・ループ・fine-tuningを追加します。

09 — Evaluating Services

「特化AI」を見抜くための質問

技術名を聞くより、失敗がどのように検出され、改善されるかを聞くと、サービスの成熟度が分かります。

モデルとデータ

  • 基盤モデルとモデルIDは何か
  • 重みを変更しているか、汎用モデルのままか
  • 独自データはRAG、学習、評価のどこで使うか
  • 情報更新・削除・権限をどう反映するか

ワークフローと品質

  • 回答前後にどんな検査があるか
  • 再試行の条件と最大回数は何か
  • 人間の承認が必要な操作は何か
  • 実業務データで何を測定しているか
強い答え「専門家プロンプトを使っています」ではなく、「この評価セットで見落とし率を測り、この条件で再検索し、引用を機械検証し、重大操作は承認を要求します」と説明できること。
この章の結論「どのモデルか」だけでなく、「何を読ませ、何を実行し、どう検証し、どう改善しているか」を聞くべきです。

10 — Where Advantage Lives

優位性はどこに宿るか

同じ基盤モデルを誰もが借りられるなら、「賢さ」の差はモデルではなく、その外側のどこかにあるはずです。どこにあるのか、そしてそれは本当に模倣困難なのかを検討します。

この章の主張：優位性は、モデルの重みにも、Skill・プロンプトのうまさそのものにも宿りません。模倣に時間・データ・組織的な蓄積を要する資産――独自データ、評価・改善ループ、業務統合――にのみ宿ります。

なぜ営利企業は自前でfine-tuningしないのか

理由内容
データ行動を変えるほど高品質・大量の学習データを、業務の片手間で用意するのは難しい
コスト学習・評価・回帰検証は前払いの投資。RAGやSkillの修正のように即座には反映できない
専門性学習パイプラインの構築・評価・劣化検知には、プロンプト設計とは別のML運用スキルが要る
動く標的数ヶ月で基盤モデルが世代交代する。旧モデルのfine-tuningは次世代モデルへ持ち越せないことが多い
目的との不一致多くの「特化ニーズ」の正体は業務知識・手順の注入であり、それはRAG／Skillの得意領域であって、fine-tuningの得意領域（振る舞い・文体・分類傾向）ではない

薄いラッパーと、厚い特化システム

模倣されやすい層

プロンプト・Skillファイルそのもの。テキストである以上、観察・抽出・推測でかなり近いものが再現できます。

模倣されにくい層

独自データ、評価・改善ループの成熟度、業務システムへの統合、利用から学ぶフィードバックの蓄積。

優位性を見抜く質問「同じ基盤モデルに競合が明日アクセスできたとして、1ヶ月で製品の核心価値を再現できるか？」再現できてしまうなら薄いラッパー。データ・評価ループ・統合が理由で再現できないなら、そこに本当の優位性があります。

独自データの価値は「量」ではなく「検索精度」

コンテキストウィンドウには物理的な上限があり、どれほど大量の独自データを持っていても、その全量を一度に読ませることはできません。だからといって独自データが無意味になるわけではなく、そもそも独自データの価値は「全部を保持して使う」ことで成立したことは一度もありません。使われる仕組みは常に、巨大だが受動的な貯蔵庫と、狭いが能動的な作業領域を、検索・選別の仕組みがつなぐという二層構造です。[9]

この二層構造はLLM以前から存在する

検索エンジンはインターネット全体を「アクティブな知識」として保持していません。巨大なインデックス（貯蔵庫）と、クエリごとに上位数件だけを選ぶランキング（検索・選別）、実際に読む検索結果ページ（作業領域）の三層です。長年の経験を持つ専門家も、案件のたびに全知識を思い出しているのではなく、関連しそうな記憶を「思い出す」選択的な想起を行っています。独自データの活用は、この構造をRAGパイプラインとして再実装しているだけです。

したがって、独自データの量そのものは優位性の必要条件であっても十分条件ではありません。検索・ランキング・重複排除・鮮度判定の精度が悪ければ、無関係な文書や重複が上位に混ざり、信号密度が下がって、むしろ回答の質を下げます（Lost in the Middle と同種の問題です）。優位性の実体は、データ量ではなく「今回必要な数件だけを高精度に選び出し続ける仕組みと、その仕組みを検証・改善する評価ループ」です。

過去の資産が効くのは「繰り返し」だけ

タスクの性質独自データ検索の有効性効いているもの
過去に類似ケースが多く存在する（よくある問い合わせ、既知の契約条項、典型的な症例）高い検索精度・鮮度・評価ループ
前例のない新規ケース（新しい規制、初めての障害、未知の症例）ほぼ無力基盤モデルの一般的な推論能力、不確実性を検知して人間へ委ねる判断
過去の資産だけでは未来を保証できない独自データの優位性は、そのタスクの何割が既知パターンの繰り返しかに比例します。本当に新規性の高い問題では、貯蔵庫の中に検索すべき正解がそもそも存在しません。ここで効くのは蓄積ではなく、モデルの生の推論力と、「これは前例に一致しない」と正直に認識できる仕組みです。
この章の結論優位性はモデルにもSkillの巧拙にも宿らず、模倣困難な資産（データ＋検索精度＋評価ループ＋統合）にのみ宿ります。そしてその資産すら、繰り返しパターンのタスクにしか効きません。

APPENDIX

TIPSと詳細資料

ここからは主線ではありません直感を補う比喩、用語、学習経路、時点依存の注意をまとめています。本文を理解するために必須ではありません。
人間とLLMの違いを一文で

人間は長年の経験を、注意・習慣・身体・環境フィードバックへ内在化しています。LLMは一般能力を持ちますが、今回の仕事固有の目的・状態・完成条件を外から与えた方が安定します。

A. 用語集
LLM大量のデータで学習し、入力に基づいてトークンを生成する言語モデル。
Weights / 重み学習で調整された数値パラメータ。モデルの長期的な振る舞いを規定。
Context一回の推論でモデルが参照できる入力と生成中のトークン領域。
System promptサービス・開発者が与える上位の指示。
Skill特定作業の手順、判断基準、資料、スクリプトを束ねた再利用モジュール。
RAG検索で関連情報を取得し、その場のコンテキストへ渡す方式。
Tool callingモデルが構造化された実行要求を返し、外側のシステムが実行する仕組み。
Harness入力構築、モデル呼び出し、ツール実行、状態管理を行う外側の基盤。
Agent loop最終回答までモデルとツールの往復を繰り返す制御。
Workflow処理順序・分岐を主にコード側で規定した流れ。
Fine-tuning追加データで重みを調整し、特定の振る舞いへ適応させる学習。
Compaction長い履歴を短い状態表現へ圧縮し、コンテキストを空ける処理。
Prompt caching共通入力の再処理を減らす仕組み。通常、コンテキスト占有は減らさない。
Evalsモデル／システムの出力を反復測定する評価セットと仕組み。
B. このセッションの学習経路
  1. Skillの核心：AIに知識を足すより、迷う地点を手順・基準・検査へ変える。
  2. 人間との違い：人間は目的保持、習慣、身体、環境フィードバックによってSkillを内在化している。
  3. 特化AIの正体：真の特化モデルと、汎用モデルを中核にした特化システムを区別する。
  4. Fine-tuningとContext：前者は重み、後者は実行時入力。Skill・RAGはコンテキストを使う。
  5. 実行ループ：プロンプトではなく外側のコードが、ツール実行と再呼び出しを行う。
  6. 二重ループ：内側は一タスク、外側は業務全体を制御するなら有効。
  7. ChatGPTの構造：モデル＋文脈構築＋ツール＋ハーネス＋安全・状態管理。
  8. 用意済みと生成：重み・実装・入力・取得情報・動的生成を分離して理解する。
C. 2026年7月時点の注意

モデル名、コンテキスト長、fine-tuning提供範囲、thinkingの扱い、サーバー側ツールなどは頻繁に変更されます。この文書では安定した概念を中心に整理し、製品固有の数値は必要最小限にしています。

OpenAIの現行モデル最適化ページは、fine-tuningプラットフォームを新規ユーザー向けに段階的に終了すると案内しています。これは「fine-tuningという概念がなくなる」という意味ではなく、特定プラットフォームの提供状況が変化しているという意味です。[5]

本ガイドは公開後、読者との壁打ちセッションを経て2026年7月24日に「10. 優位性の所在」章を追加しました。

D. 最終的な一文
LLMサービスの本質は、巨大なモデルに全部を任せることではない。モデルが得意な曖昧な意味判断と、コードが得意な確実な制御を分業し、必要な情報だけを必要な瞬間に渡し、現実の結果で検証することである。
