Privacy / Consent — Adobe & Google 比較ノート

Cookie、GDPR、ePrivacy、Adobeの関係を
仕様定義できる粒度まで整理する

この資料は、「cookieless なら大丈夫」という単純化を避け、何が端末保存の論点か、何が個人データ処理の論点か、Adobe側でどこまで制御できるかを分けて読めるように再構成した学習ノートです。 比較対象として Google Consent Mode の cookieless ping も扱い、「cookieless」という同じ言葉が指す実装の幅を具体例で示します。

対象: Web / Analytics / Personalization / Consent 軸: 法務 × 実装 × 運用 結論: Cookie有無だけでは決まらない 注: 法的助言ではない

まず押さえるべき全体像

cookie の有無は「入口」の論点。

ePrivacy は、端末への保存・アクセスを中心に見ます。cookie を使わない設計でも、他の識別子や端末アクセスがあれば別途論点が残ります。

GDPR は「処理するデータ」の論点。

IP、User-Agent、URL、ECID、CRM ID、イベントIDなど、個人データになり得るものが処理されれば、法的根拠・透明性・保存期間・第三者提供などを別に検討します。

cookieless = GDPR準拠、ではありません。

Cookieを書かなくても、データ送信や相関処理の設計次第で、GDPRの適用は普通に残ります。逆に、cookie を使っていても、用途・情報量・法的根拠が整理されていれば実務上成立する場合があります。

1. cookieless とは何か

cookieless は「Cookieを使わない」ことを意味しますが、実装としては少なくとも次の4パターンがあります。

  • 保存しない: 端末にIDを残さず、都度のイベントだけ送る。
  • 保存するがCookie以外: LocalStorage などを使う。
  • Server-sideで識別する: URLやIP、ヘッダ、リクエストIDを手掛かりにする。
  • 匿名っぽく見せる: 実際には相関可能性が残る設計。

読み替えのコツ

技術用語としての cookieless は、法的に「同意不要」を意味しません。評価対象は、保存される情報、送信される情報、相関可能性、目的の4点です。

2. GDPR とは何か

GDPR は 個人データの処理 を規律します。cookie そのものではなく、個人データに該当する情報を、どの目的で、どの法的根拠で、どの範囲まで処理するかを見ます。

  • 法的根拠: 同意、契約、法的義務、重要な利益、公的任務、正当利益。
  • 重要論点: 透明性、目的限定、データ最小化、保存制限、第三者提供、越境移転。
  • consent は「自由意思・特定・十分な情報・明確な同意」が必要。

注意: 「ポリシーでそう書いたから GDPR OK」ではありません。文言ではなく、実データフローが決まります。

コラム: Google Consent Mode の「cookieless ping」 — cookieless の実装例

「cookieless」を実装レベルで理解する具体例として、Google Consent Mode(Google Ads / GA4)の cookieless ping を見ておきます。Adobe とは別ベンダーの仕組みですが、cookieless の実装パターンの幅を示す好例です。

仕組み

ユーザーが同意を拒否した状態では、タグは Cookie を保存・参照せず、代わりに軽量な「cookieless ping」をサーバーへ送信します。ping にはタイムスタンプ・User-Agent・Referrer といったブラウザが受動的に付与するヘッダー情報や、広告クリック情報の有無、同意状態を表すブール値、ページロードごとのランダム値など、個人を特定しない粗粒度の情報のみが含まれます。

目的

Google はこの ping 群を用いて、同意を拒否したユーザー分のデータギャップを モデリング(behavioral modeling) で補完し、コンバージョン等の指標を推定します。同意が得られた時点で、Cookie ベースの通常計測に切り替わります。

Adobe との違い: これは「Cookie を送らない = 何も送らない」ではなく、「個人を特定しない情報だけを送り、統計的に補完する」という設計です。Adobe Web SDK の defaultConsent: "pending"(データをローカル保存し送信しない)とは設計思想が異なる点に注意してください。

3. ePrivacy とは何か

ePrivacy は、端末への保存または端末からのアクセスを中心に扱います。実務では、cookie、LocalStorage、セキュリティトークン、端末内の類似技術が対象候補になります。

  • 原則: ユーザーの端末機器への保存・アクセスは同意が必要。
  • 例外: サービス提供に不可欠なもの、ユーザー明示要求に必要なものなど。
  • 位置づけ: GDPR と競合するのではなく、前段の「端末側のルール」。

要点: ePrivacy を外れても GDPR は残り得ます。逆も同様です。

4. 3つの関係を一枚で見る

論点 cookieless ePrivacy GDPR
対象 技術の選択 端末保存・アクセス 個人データ処理
同意の要否 自動では決まらない 原則要る 法的根拠により決まる
評価ポイント 保存しないか、識別しないか 端末への書き込み・読み出し 識別可能性、目的、相関性、保存期間

技術と法規制のレイヤーが違うため、仕様は両方に対して作る必要があります。

5. Adobe の技術はどこで効くのか

Adobe では、Web SDK / Edge / ECID / Analytics / Target / Privacy Service の組み合わせで、同意前後のデータ収集を設計できます。重要なのは、何を止めるか、何を残すか、どのタイミングで開始するか を明文化することです。

Web SDK defaultConsent / setConsent

defaultConsent は、同意確定前の扱いを決める起点です。`in` / `out` / `pending` の3値で制御し、`setConsent` は同意が変わったときに送信されます。

設計上は、「初回ロード時に何を送らないか」「同意確定後に何を開始するか」を分けて決めます。

Identity ECID / consent

同意と ID は密接に関連しています。Web SDK は同意の状態に応じて ECID の生成や ID Cookie の設定、Edge Network への送信タイミングに影響します。

同意が確定する前に ECID を作るかどうかは、仕様の中核です。

Analytics 計測と識別

Analytics は計測目的の処理ですが、一般に訪問者識別や継続計測の設計が含まれます。Cookie を止めても、イベントの粒度や送信項目次第で個人データ性は残り得ます。

Target パーソナライズ

Target はテストやオファー配信のために cookie を使う構成があり、マーケティング/パーソナライズの同意論点が強くなりやすい領域です。

6. Adobe Web SDK の同意設計で見える事実

1

defaultConsent は「同意前の既定値」

`defaultConsent` は `setConsent` を呼ぶ前の収集挙動を決めます。値は `in` / `out` / `pending` のみで、設定しない場合は `in` です。ページごとに再設定が必要で、ページロード間で永続しません。

2

setConsent は同意確定後の状態を反映

`setConsent` は、同意が変更されたときにのみサーバー呼び出しを行い、Web SDK 内にユーザーの同意状態を保持します。Adobe は同意ダイアログの状態を別途保存することを推奨しています。

3

ECID と consent は連動する

同意と ID は密接に関連し、Web SDK が ECID を生成し、ID Cookie を設定し、Edge に送信するタイミングに影響します。つまり、「同意をどう判定するか」ではなく、「どの時点で ID を作るか」まで仕様化する必要があります。

4

Privacy Service は運用面の別レイヤー

Adobe の Privacy Service は、収集済みデータに対する削除やエクスポート等のプライバシー要求を扱う運用基盤です。これは consent 設計の代替ではなく、別のコンプライアンス機能です。

7. 顧客と決めるべき仕様項目

「同意が必要かどうか」だけを聞くと議論が止まります。実務では、次のように分解すると決まりやすくなります。

8. 典型パターン

パターン A: 同意後に全部開始

EU など consent 要件が強い地域で、初回ロードでは `pending` または `out` にしておき、同意後に ECID / Analytics / Target を開始する。

パターン B: 必須計測のみ先行

必須の運用指標だけ先に取り、広告・パーソナライズは同意後に開始する。項目分離が甘いと、結局すべて止まる。

パターン C: cookieless風だが識別可能

cookie は使わなくても、IP・UA・URL・リクエストIDで相関できるなら、GDPR 上の評価は残る。ここを「匿名化」と言い切るのは危険。

パターン D: cookieless ping + モデリング(Google型)

同意拒否時は個人を特定しない粗粒度 ping のみ送信し、統計モデリングで補完する。データ量は減るが完全な計測停止にはしない設計。

9. 実務判断のフレーム

A

端末に何か書くか

書くなら ePrivacy の論点。cookie 以外の保存先も含めて確認。

B

個人データか

IP、ID、行動ログ、URL、デバイス情報が相関可能なら GDPR の論点。

C

何を根拠に処理するか

同意か、正当利益か、必要性か。カテゴリごとに分けて判断。

【例】
- EU訪問者の初回表示時: defaultConsent = pending
- 同意未確定: Analytics/Target/ID生成を開始しない
- 同意取得後: setConsent 実行、ECID生成、許可済みソリューションのみ開始
- 同意撤回時: out へ変更、以後の送信停止、既存データの削除要求は Privacy Service で処理

11. まとめ

結論はシンプルです。

  • cookieless は技術の選択であって、法的結論ではない。同じ「cookieless」でも、Adobe の pending(未確定なら送信・保存しない)と Google の cookieless ping(個人特定不可情報のみ送りモデリングで補完する)は設計思想が異なる。
  • ePrivacy は端末への保存・アクセスを見る。
  • GDPR は個人データ処理を見る。
  • Adobe は同意前後の挙動をかなり細かく設計できるが、どのデータをいつ止めるかは顧客要件として確定する必要がある。

実務の一言: 「同意が必要か」ではなく、「何をどの順番で、どこまで処理するか」を先に決めると、法務・マーケ・実装が揃いやすくなります。
