    Adobe Analytics セグメント：データ抽出装置として理解する

    このドキュメントについて

    Adobe Analytics のセグメントを「データ抽出装置」として理解するための包括ガイドです。セグメントで条件を指定した時に「何が起こるか」を仕組みのレベルで解説し、条件の複合・除外・順次それぞれの挙動を自分で逆算できるようになることを目標とします。

    対象読者：AA の基本操作は知っているが、除外や順次の挙動で意図しない結果に直面したことがある実務者。

    AA と CJA の用語対応・略式表示の規約

    このドキュメントは AA の用語（訪問者・訪問・ヒット）で統一しています。CJA では人物（Person）・セッション（Session）・イベント（Event）に相当します。仕組みは同じです。

    略式表示について：本文では AA 用語で記述しますが、ID の略式表示は CJA の頭文字 E / S / P（event / session / person）を使用します。AA 用語では「visit」と「visitor」がいずれも v で始まるため区別できないことが理由です。具体的には、ヒット ID は E1・E2…、訪問 ID は S1・S2…、訪問者 ID は P1・P2… と表記します。

    理解度の確認には AA_segment_quiz.html（100 問のクイズ）を利用してください。

    1. AA のデータモデル：セグメントが操作する対象

    1-1. 3 層の階層構造

    AA のデータは以下の 3 層で管理される。

    訪問者（Visitor）
  └─ 訪問（Visit）
       └─ ヒット（Hit）
    レベル意味識別子
    訪問者特定デバイスまたは人物のライフタイム全体visitor ID
    訪問一連の連続したセッション（30 分無操作で終了）visit ID
    ヒット個々のページビュー・リンククリック・カスタムイベントhit ID

    1-2. 識別子の共有関係

    同一訪問に属するヒットは、同じ visit_id を共有する。同一訪問者に属する訪問・ヒットは、同じ visitor_id を共有する。共有関係は外側のコンテナを共有しているかで決まる。

    visitor_id = P1
    visit_id = S1（1/1 10:00–10:12）
    E1: home E2: product E3: cart
    visit_id = S2（1/3 14:00–14:08）
    E4: checkout E5: order
    • E1〜E3 は同じ visit_id（S1）を持つ → 同一訪問内のヒット
    • E1〜E5 は同じ visitor_id（P1）を持つ → 同一訪問者のヒット（訪問は異なる）
    • E4 と E5 は同じ visit_id（S2）を持つ → 別訪問だが同じ訪問者
    訪問データをテーブルレイアウトで表示
    hit_iddateTimepagevisit_idvisitor_id
    E11/1 10:00homeS1P1
    E21/1 10:05productS1P1
    E31/1 10:12cartS1P1
    E41/3 14:00checkoutS2P1
    E51/3 14:08orderS2P1

    1-3. 「取得」とは何か

    セグメントの「取得」とは、特定の識別子を持つ行を結果セットに含める操作である。セグメントが「一致した」と判定した場合、AA はその識別子（hit ID / visit ID / visitor ID）に等しい行をすべてレポートに返す。

    2. コンテナの本質：評価スコープと返却スコープの一体性

    2-1. コンテナの 2 つの役割

    コンテナは以下の 2 つの役割を同時に担う。

    役割定義
    評価スコープ条件をどの粒度で判定するか
    返却スコープ条件が通った時、何を返すか

    評価スコープと返却スコープは常に同じ（≡）である。

    2-2. 3 コンテナの動作比較

    コンテナ評価の対象条件が通った時に返すもの
    ヒット個々のヒット 1 件ずつ条件に一致した そのヒットのみ
    訪問訪問内の全ヒット群条件が通った 訪問の全ヒット
    訪問者訪問者の全ヒット群条件が通った 訪問者の全ヒット

    3. 複合条件の評価メカニズム：AND/OR とスコープの関係

    3-1. 単一コンテナ内の AND/OR

    AND・OR の評価はコンテナのスコープ内で行われる。

    ヒットコンテナ内の AND：

    Hit
    page=home AND page=product

    1 つのヒットに page=home と page=product の両方が存在しなければならない。1 ヒットに page は 1 値しか持てないため、結果は常に 0 件。

    訪問コンテナ内の AND：

    Visit
    page=home AND page=product

    同一訪問の中のどこかに page=home のヒットと page=product のヒットの両方が存在すること。別々のヒットに分かれていても OK。

    条件一致ヒット ○ ＝ そのコンテナで返却される
    P1
    home product
    P2
    home contact
    • Hit コンテナ：1 ヒットに page=home と page=product は共存できないため全 0 件
    • Visit コンテナ：S1 は home・product の両ヒットを持つ → S1 全ヒット返却。S2 は product なし → 除外
    訪問データをテーブルレイアウトで表示（○ = 返却、- = 返却されない）
    dateTimepagevisit_idvisitor_id[Hit] home AND product[Visit] home AND product
    1/1 10:00homeS1P1-○
    1/1 10:05productS1P1-○
    1/2 09:00homeS2P2--
    1/2 09:10contactS2P2--

    • cart 訪問と checkout 訪問は 異なる訪問でも OK

    3-3. 異なるスコープを AND で組み合わせた場合

    外側コンテナが全体の返却スコープを決める。内側の条件はその範囲内で真偽を返すだけである。AA の Orders は注文完了ページ（complete）のヒットでカウントされるものとする。

    Visit
    page=product
    AND
    Visitor
    Orders > 0

    返却スコープ：訪問（Visit コンテナが最外）
    評価：この訪問に page=product があり、かつこの訪問者がライフタイムで Orders ＞ 0（過去に注文を完了している）

    条件一致ヒット ○ ＝ 返却される
    P1
    home product
    P2
    home product cart complete+ order
    home contact
    • S1（P1）：product ヒットあり、しかし P1 は注文経験なし（complete ヒットなし） → [Visitor] Orders > 0 不成立 → 訪問ごと除外
    • S2（P2）：product ヒットあり・complete で order が記録されているため Orders=1 → 両条件成立 → S2 の全ヒットを返却
    • S3（P2）：訪問者として注文経験があっても、この訪問に product ヒットなし → [Visit] page=product 不成立 → 除外
    訪問データをテーブルレイアウトで表示（○ = 返却、- = 返却されない）

    P2 は Orders > 0 を満たすが、返却されるのは P2 の全データではなく 条件を満たした訪問（S2）のデータのみ。返却スコープは最外コンテナ（Visit）が決める。

    逆の入れ子構造：外側が小・内側が大のケース

    コンテナは Visitor → Visit → Hit の順（外が大・内が小）に限らない。逆順——外側が Hit・内側が Visitor——でも設定できる。原則は変わらない：外側コンテナが返却スコープを決め、内側コンテナは条件の真偽を返す。以下 2 つのセグメントを比較する。

    Hit
    page=cart
    AND
    Visitor
    Orders > 0
    Visitor
    page=cart
    AND
    Orders > 0

    「ヒット単位」は最外が Hit のため返却もヒット単位、「訪問者全体」は最外が Visitor のため訪問者の全データが返却される。

    条件一致ヒット ○ ＝ そのセグメントで返却される
    P1
    home cart product
    P2
    home cart complete+ order
    • P1：注文経験なし（complete なし）→ [Visitor] Orders > 0 不成立 → 両パターンとも全行 -
    • P2 / ヒット単位：cart ヒットのみ返却。home・complete は page≠cart のため -
    • P2 / 訪問者全体：cart あり・complete で order 記録あり → Visitor 条件成立 → home・cart・complete すべて返却
    訪問データをテーブルレイアウトで表示（○ = 返却、- = 返却されない）
    dateTimepageeventvisit_idvisitor_id返却: ヒット単位返却: 訪問者全体

    逆の入れ子の使いどころ

    「訪問者属性で絞り込みたいが、返却は特定ヒットだけにしたい」場面で有効。外側を Visitor にすると対象訪問者の全データが返ってくるが、外側を Hit にすれば条件を満たすヒットだけに絞れる。

    4. 否定条件の意味：単純な「存在しない」ではなく「それ以外のヒットが存在する」

    否定条件（!=・does not contain・does not exist 等）はコンテナのスコープ内で 条件を満たすヒットが存在するか として評価される。AND/OR と同じ評価モデルが適用されるため、直感と外れた結果になりやすい。

    Visit
    page != plp

    これは「この訪問の中に page が plp でないヒットが存在するか」を評価する。home・product・cart など plp 以外のページを 1 件でも含む訪問なら true になる。

    ストリーム[Visit] page != plp意図と一致するか
    home → product → cart成立（home など plp 以外のヒットあり）〇
    home → plp → product成立（home が plp 以外のヒットとして存在）× 意図は「plp なし」なのに通過する
    plp のみ不成立（すべてのヒットが plp）〇

    plp のみの訪問は除外されるが、plp と他ページが混在する訪問は通過してしまう。

    スコープ別の動作比較：

    条件評価の意味
    [Hit] page != plpそのヒットが plp でないか（直感と一致する）
    [Visit] page != plp訪問内に「plp でないヒット」が 存在するか（他のページが 1 件でもあれば true）
    [Visitor] page != plp訪問者のヒット全体に「plp でないヒット」が 存在するか（同上）

    ヒットコンテナでは否定条件が直感通り機能する。訪問・訪問者コンテナで「この訪問に plp が一切ない」を表現したい場合は否定条件では届かず、Exclude コンテナが必要になる（5 節で詳説）。

    5. 除外コンテナのメカニズム

    5-1. 除外コンテナの本質

    除外コンテナは「行を物理的に削除する」のではなく、スコープ単位で否定条件を返す 仕組みである。

    除外コンテナ否定の単位意味
    Exclude Hitヒットこのヒットが条件を満たす → このヒットを除外する
    Exclude Visit訪問この訪問が条件を満たす → この訪問を除外する
    Exclude Visitor訪問者この訪問者が条件を満たす → この訪問者を除外する

    5-2. スコープ一致が正しい除外の鍵

    「plp を含まない訪問を取得したい」という要件に対して、3 通りのアプローチを比較する。

    パターン A：否定条件

    Visit
    page=home
    AND
    page != plp

    評価：訪問内に「page=home かつ page≠plp のヒット」が存在するか。page=home のヒットは常に page≠plp なので、実質的に [Visit] page=home と等価。
    → plp あり の訪問も通過 ×

    パターン B：Exclude Hit（スコープミスマッチ）

    Visit
    page=home
    AND
    Exclude Hit
    page=plp

    評価：Exclude Hit は各ヒットを個別に評価し、page=plp のヒットを除外（false）、それ以外を通過（true）とする。AND はヒットレベルで結合されるため「page=home かつ [Exclude Hit] を通過したヒット」を探す。page=home のヒットは plp ではないので [Exclude Hit] を必ず通過する。
    → こちらも実質的に [Visit] page=home と等価。plp あり の訪問も通過 ×

    パターン C：Exclude Visit（正しい）

    Visit
    page=home
    AND
    Exclude Visit
    page=plp

    評価フロー：

    1. この訪問に page=home のヒットが存在するか → true/false
    2. この訪問に page=plp のヒットが存在するか → true ならば 訪問全体を除外（Exclude Visit）
    3. 両条件が成立する訪問のみを返す

    → home あり・plp なし の訪問のみ返る 〇

    条件一致ヒット ○ ＝ そのパターンで返却される
    P1
    home product
    home plp product
    P2
    home contact
    • S1・S3（plp なし）：A・B・C すべて条件成立 → 全ヒット返却
    • S2（plp あり）：A・B は visit が通過 → plp ヒット自体も含む S2 全ヒット返却 × / C は訪問全体を除外 → すべて - 〇

    3 パターンの違いまとめ：

    パターン評価の単位「plp なし」を表現できるか等価な意味
    否定条件 page != plpヒット×「plp でないヒットが存在する訪問」
    [Exclude Hit] page=plpヒット×plp ヒットを除外するが AND がヒットレベルで結合 → 「page=home のヒットがある訪問」

    スコープミスマッチの原則

    否定条件と Exclude Hit はどちらもヒットレベルで評価される。訪問・訪問者スコープで「この条件を含まない」を表現するには、スコープが一致した Exclude コンテナが必要。

    5-3. よくある誤りと正解パターン

    やりたいこと誤ったセグメント正しいセグメント

    6. 順次セグメントのメカニズム

    順次セグメントは 時系列の関係性（A の後に B、A から N 時間以内に B など）を扱う仕組み。以下の構成要素から成る：

    • コンテナスコープ：順次セグメントも通常のコンテナと同じく Visit スコープか Visitor スコープを選べる。
      • Visit スコープ：シーケンスは 1 訪問内で完結する必要がある（A と B が同じ訪問内に存在するか）
      • Visitor スコープ：複数訪問にまたがってシーケンスを評価できる（A と B が異なる訪問でも可）
    • THEN 演算子（6-1）：チェックポイント間の順序を定義
    • After / Within 制約（6-2〜6-4）：チェックポイント間の時間窓を定義
    • 返却モード：シーケンス成立後にどこまでのデータを返すかを 3 つから選択
      • Include Everyone（デフォルト）：シーケンスを qualifying 条件として使い、条件を満たした訪問者/訪問の 全データ を返す
      • Only After Sequence（6-5）：シーケンスを構成する 最後の INCLUDE チェックポイント以降 のデータのみを返す
      • Only Before Sequence（6-6）：シーケンスを構成する 最初の INCLUDE チェックポイントまで（その INCLUDE 自体を含む）のデータを返す
      • Only After と Only Before の 併用（コンテナ AND 結合による区間抽出）は 6-7 で扱う
    • EXCLUDE チェックポイント（section 7）：シーケンス内に「不在の証明」や「収集範囲の境界」を組み込む。位置別の役割と Only After/Before との組み合わせまで section 7 で扱う
    前提

    本節 6-1〜6-4 の例示はすべて Include Everyone（デフォルトモード）を前提とする。Only After / Only Before の挙動は 6-5・6-6 で扱う。スコープは Visit／Visitor のどちらかを使い分けるが、本節の例示は基本的に Visitor スコープ（複数訪問にまたがる例を示すため）を使用する。

    6-0. 順次セグメントの 5 原則（Adobe 公式）

    Adobe Customer Success Webinar で示された、順次セグメント全体を貫く 5 つの原則。section 6・7 のすべての挙動はこの原則から導かれる。

    1. "All the Include conditions in the THEN definition must be encountered, in order, to begin matching."
    2. "Matching continues until and unless an Exclude condition is triggered, when it then stops."
    3. "If the Include sequence is observed multiple times in the container scope, each of those sequences will independently evaluate and add to the data returned."
    4. "Add WITHIN / AFTER conditions to force the proximity you require. (This is often needed)."
    5. "Validate every time you try something new. You will mistakenly assume the nature of your data or your sequential filter definition, at some time."

    — Adobe Customer Success Webinar (Mastering Sequential Logic: Starts and Stops)

    1. INCLUDE は 順序通りすべて出現してはじめてマッチ開始6-1（THEN 演算子のスキャンモデル）
    2. マッチは EXCLUDE が触発されるまで継続し、触発時に停止section 7（特に 7-4・7-5 の範囲終端）
    3. 同じ INCLUDE シーケンスが複数回出現すれば それぞれ独立に評価され、返却データに加算される（greedy）6-5・6-6 の greedy デモ
    4. 必要な近接性（時間距離）は WITHIN / AFTER で明示的に指定する6-2・6-3・6-4
    5. 新しい定義を試すたびに 必ず検証 する。データや定義について必ずどこかで思い込みが発生するsection 8 の読解手順、複合設計の検証習慣
    原則 3（greedy）の含意

    1 訪問者の中で同じシーケンスが複数回成立すれば、それぞれの成立点から個別に Only After/Before の収集が走り、結果として 複数の区間データが連結されて返却 される。これは 6-5・6-6 の greedy ケースで明示的に示している。

    原則 5（検証）の重要性

    順次セグメントは構文の見た目から推測した挙動と実際の挙動が乖離しやすい。EXCLUDE の位置・モードの組み合わせ・コンテナスコープのいずれを変えても結果が大きく変わる（section 7 のまとめ表参照）。本書の hitstream 例示と同じ要領で、自分のデータでも必ず一致／不一致パターンを検証してから本番運用に入ること。

    6-1. THEN 演算子：スキャンモデルの基本

    順次セグメントは hit ストリームを 時系列順にスキャン するモデルで動作する。

    動作原理：

    1. ヒットストリームを先頭からスキャンし、チェックポイント A に一致するヒットを探す
    2. A が見つかった地点を「通過点」として記録する
    3. 通過点以降のストリームを再スキャンしてチェックポイント B を探す
    4. B が見つかればシーケンス成立。見つからなければ次の A 候補から繰り返す

    greedy（欲張り）な動作： シーケンスが複数の方法で成立する場合、AA は 最大データ量を返す組み合わせ を選ぶ。

    Visitor
    Hit
    page=A
    THEN
    Hit
    page=B
    シーケンスのチェックポイント ○ ＝ 返却される
    P1
    A B
    P2
    B A
    P3
    A C B
    P4
    A B A B
    • P1：A の後に B → 成立、訪問者の全データ返却
    • P2：B の後に A はあるが、A の後に B がない → 不成立
    • P3：A の後に B あり（C は無視される）→ 成立
    • P4：A → B → A → B、最初の A→B で成立。greedy で最大データを返す

    6-7. Only After と Only Before の併用：区間抽出

    Only After Sequence と Only Before Sequence は、Visitor コンテナの中で 2 つの順次サブグループとして AND 結合 することで併用できる。両者の返却範囲の共通部分が返却され、2 つのイベント間のデータ区間を切り出す ことができる。

    Visitor
    Visitor / Only After Sequence
    Hit
    page=A
    THEN
    Hit
    page=B # 開始点
    AND
    Visitor / Only Before Sequence
    Hit
    page=C # 終了点
    THEN
    Hit
    page=D

    Only After A→B は「B 以降」を、Only Before C→D は「C 以前」を返す。AND の共通部分は B から C までの区間（B・C 自身も含む）。

    データ収集区間（B〜C）
    シーケンスのチェックポイント ○ ＝ 返却される
    P1
    pre A X B Y Z C Q D post
    P2
    pre A X B Y Z post
    P3
    pre X Y Z C Q D post
    P4
    A B A B C D C D
    • P1（両シーケンス成立）：A→B・C→D ともに成立 → Only After 開始点 ＝ B、Only Before 終了点 ＝ C → AND 共通部分 B〜C 区間（B・Y・Z・C）が返却される
    • P2（C→D 不在）：A→B は成立するが C→D が存在しない → Only Before 側が不成立 → セグメントが訪問者にマッチしない → 全データ返却なし
    • P3（A→B 不在）：C→D は成立するが A→B が存在しない → Only After 側が不成立 → セグメントが訪問者にマッチしない → 全データ返却なし
    • P4（greedy）：A→B が 2 通り、C→D が 2 通り成立可能。greedy により Only After は 最初の A→B（最初の B が開始点）、Only Before は 最後の C→D（最後の C が終了点）を採用 → 最大窓 最初の B〜最後の C が返却される
    活用例

    「ログイン後（Only After page=login THEN page=home）から、購入完了前（Only Before page=cart THEN event=order_confirm）までのブラウジング行動」など、特定のイベント区間のみのデータ を分析したい場面で有効。

    7. 順次セグメント + 除外チェックポイント

    順次セグメントの中に EXCLUDE チェックポイントを置くと、シーケンスに「不在の証明」や「収集範囲の境界」を組み込める。EXCLUDE の位置（最初・途中・最後）によって役割が根本的に異なる。Only After / Only Before モード（6-5, 6-6）と組み合わせると、収集の起点と終端の両方を絞り込むことができる。

    7-1. 最初が EXCLUDE：(EXCLUDE A) THEN B

    "Identify visitors who visited one page without ever going to another page. For example, people that checked out a purchase without ever visited the home page."
    — Adobe Analytics Documentation (Sequential segments)

    "give me the people who interacted with email but not with web before email"
    — Adobe Customer Success Webinar (Mastering Sequential Logic)

    意味（Include Everyone 既定モード）：「B に到達した時点で、それより前に A が存在しないこと」

    EXCLUDE は qualifying 条件（不在の証明） として機能する。A が B より前に存在する訪問者は セグメントに不一致 となり、何も返却されない。Only After Sequence の収集開始点の判定にも使われない。

    モードによる挙動の違い

    同じ位置の EXCLUDE でも、Only Before モードと組み合わせると後方終端として機能する（C で打ち切られるが、シーケンス自体は成立し A と C の間のデータが返却される）。詳しくは 7-5 を参照。

    Exclude Hit
    page=A
    THEN
    Hit
    page=B
    シーケンスのチェックポイント ○ ＝ 返却される
    P1
    A B
    P2
    C B

    意味：「A の後 C に到達したが、A と C の間に B が出現しなかった」

    "The subset(s) of a Person's data, prior to a matched sequence of Web then App, but not beyond (earlier than) an Email touch. ... It is a series of events ending with the inclusive sequence, going back until any exclude checkpoint is observed."
    — Adobe Customer Success Webinar (Mastering Sequential Logic: Starts and Stops)

    Only After + 終端 EXCLUDE の 鏡像。Only Before モードでは、最初の EXCLUDE が qualifying ではなく後方終端 として振る舞う：シーケンスは「A が存在する」という条件で成立し、Only Before の終了点（A）から時系列を遡って収集を続け、特定イベント（C）に到達した時点で打ち切る。

    7-1 との違い

    同じ (EXCLUDE C) THEN A でも、Include Everyone モード（7-1）では C が存在すると不一致でデータなし、Only Before モード（7-5）では C は終端として機能し、C と A の間のデータが返却される。Only After/Before モードは EXCLUDE を「収集範囲を絞る境界」として再解釈する。

    Visitor / Only Before Sequence
    Exclude Hit
    page=C # 後方終端（C より前は除外）
    THEN
    Hit
    page=A # 最初の INCLUDE → 収集終了点
    シーケンスのチェックポイント ○ ＝ 返却される
    P1
    pre C X Y
    Z A post
    • S1：pre は C より前にあるため後方終端で除外、C 自身も EXCLUDE で除外、X・Y は C と A の間にあるため収集対象
    • S2：Z は A より前（収集範囲内）で収集対象、A 自身は最初の INCLUDE であり境界として収集対象、post は A 以降のため対象外
    訪問データをテーブルレイアウトで表示（○ = 返却、- = 返却されない）
    dateTimepagevisit_idvisitor_id返却

    1/2 09:05AS2P1○
    1/2 09:10postS2P1-

    7-6. 実用例：申し込み後の「直後 1 セッション」を取得する

    App 申し込みイベントが発生した訪問の 直後の 1 セッションのみ を抽出するセグメント。Only After で「申し込みイベント以降」を指定し、終端 EXCLUDE で「次の訪問が始まったら収集終了」を表現。

    Visitor / Only After Sequence
    Visit
    App submit event # 申し込みが起こった訪問
    THEN
    Visit
    Day exists # 起点（この訪問の開始ヒット以降）
    THEN
    Exclude Visit
    Day exists # 終端（次の訪問が始まったら収集終了）

    この構成で「申し込み後の最初の 1 セッション」に限定されたデータを返す。

    7-7. EXCLUDE の位置と役割（まとめ）

    位置構成例Include Everyone（既定）Only After モードOnly Before モード
    最初(EXCLUDE A) THEN Bqualifying（B より前に A が存在しない）不明（明確な情報源なし）後方終端（B から遡り、A 直前で打ち切り）
    途中A THEN (EXCLUDE B) THEN Cqualifying（A と C の間に B が存在しない）不明（明確な情報源なし）不明（明確な情報源なし）
    最後A THEN B THEN (EXCLUDE C)qualifying（B 以降に C が存在しない）前方終端（B 起点で C 直前まで）不明（明確な情報源なし）
    重要：モードによる EXCLUDE の意味の切り替わり

    Include Everyone モードでは すべての位置の EXCLUDE が qualifying（条件違反すれば不一致で返却なし）として機能する。Only After / Only Before モードと組み合わせると、収集の進行方向にある EXCLUDE が範囲終端として再解釈される（条件違反でもセグメントは成立し、終端で収集を打ち切る）。Only After + 終端 EXCLUDE（7-4）と Only Before + 起点 EXCLUDE（7-5）が公式 Webinar で言及されている代表的な使い方。「不明」と記したセルは現時点で明確な情報源を確認できなかった組み合わせであり、実装の挙動は実データで検証すること。

    おまけ：最小構成（INCLUDE 1 個 + EXCLUDE 1 個）

    THEN 演算子は最小 2 個のチェックポイントから利用でき、片方を EXCLUDE に設定してもよい。A THEN (EXCLUDE C) や (EXCLUDE C) THEN A のような INCLUDE 1 個 + EXCLUDE 1 個 も有効な順次セグメント定義となり、「シーケンス」は単一チェックポイントでもよい。

    "Only two checkpoints are needed to use THEN, even if one is configured to EXCLUDE."
    "The inclusive sequence is simply 'Web', which starts to match a series of consecutive events going forward in time. If it finds Email, it stops matching."
    "At a minimum, every Person's Web hits will be retrieved here."
    — Adobe Customer Success Webinar (Mastering Sequential Logic: Starts and Stops)

    挙動はモードと配置の組み合わせで上のまとめ表通りに分かれる。例えば A THEN (EXCLUDE C) を Only After モードで使えば 7-4 の縮約版（A から C 直前まで収集）、(EXCLUDE C) THEN A を Only Before モードで使えば 7-5 の縮約版（A から遡り C 直前まで収集）として動作する。

    最低保証ライン（"At a minimum..."）

    Only After + 終端 EXCLUDE / Only Before + 起点 EXCLUDE のいずれでも、INCLUDE が出現していれば 最低でもそのチェックポイント自身は必ず返却される。EXCLUDE による打ち切りが発生しなくてもデータ末尾（または先頭）まで収集が続くため、INCLUDE が成立している限り空集合にはならない。

    8. 複合設計の読み方

    8-1. セグメントを「読む」処理手順

    複雑なセグメントに直面した時は、以下の手順で評価を追う。

    1. 最外コンテナのスコープを確認する（= 返却スコープ）
    2. 子コンテナ・条件を内側から外側に向けて評価する
    3. 除外コンテナが見つかったら、そのスコープで否定を適用する
    4. 順次条件が含まれる場合、スキャンモデルで通過点を特定する
    5. Only After/Before が指定されていれば、起点/終点でデータを切り出す

    8-2. 読み解き例

    例 1（複合除外）：

    Visitor
    Visit
    page=product
    AND
    Exclude Visit
    event=purchase
    • 返却スコープ：訪問者（Visitor コンテナ）
    • 条件 1：product ページを含む訪問が存在する（Visit コンテナ → 真偽値）
    • 条件 2：purchase イベントを含む訪問が存在しない（Exclude Visit → 訪問単位で否定 → 真偽値）
    • 結果：product を見たが購入はしていない訪問者の全データ 〇
    条件一致ヒット ○ ＝ 返却される
    P1
    product cart
    checkout / purchase
    P2
    product cart
    info
    • P1：product 訪問あり（S1）、しかし purchase 訪問も存在（S2）→ Exclude Visit 発動 → P1 全体除外
    • P2：product 訪問あり（S3）、purchase 訪問なし → 条件成立 → P2 全データ返却

    • 時間制約の基点：product 閲覧訪問の終了時点（A を離れた時点）

    8-3. 設計時のチェックリスト

    除外を設計する時：

    • 「何を除外したいか」の粒度は？ヒット・訪問・訪問者のいずれか？
    • Exclude コンテナのレベルはその粒度と一致しているか？
    • Exclude Hit を訪問コンテナの AND に入れていないか？（スコープミスマッチに注意）

    順次を設計する時：

    • greedy の影響で意図しない早期マッチが起きないか？
    • After/Within の基点は「A を離れた時点」であることを確認しているか？
    • EXCLUDE の位置は最初・途中・最後のどこか？それぞれの役割を把握しているか？

    Only After/Before を設計する時：

    • 起点/終点は何のヒットに相当するか？
    • データ収集を途中で止めたい場合、終端 EXCLUDE を設定しているか？
    • 複数回シーケンスが成立する場合、greedy でどの成立が選ばれるか確認しているか？
